CRE AgentOS

A multi-agent AI platform built to solve the enterprise trust problem

Built solo · Python + Streamlit · Anthropic API · Tavily API · Demo on local machine

The problem

I started with one question: why do enterprise users try AI tools, see the capability, and still not adopt them?

After researching adoption patterns in commercial real estate, finance, and legal — domains where a single wrong answer ends careers — I kept arriving at the same answer. It's not a capability problem. It's a trust problem. Users can't tell when to believe the output.

The standard industry response is a disclaimer. "AI can make mistakes. Please verify outputs." That's an abdication of product responsibility. I wanted to build something that earned trust architecturally — not through better prompting or more confident outputs, but through structural honesty about uncertainty.

I chose CRE as the domain because the trust stakes are high (a single acquisition decision can involve tens of millions of dollars), the workflows are genuinely multi-dimensional, and market data changes constantly — creating a natural use case for temporal monitoring of AI outputs.

Key product decisions

Why a trust layer instead of better prompting?
Better prompting makes outputs more confident. More confidence without more accuracy makes the trust problem worse. The Red Team and Drift Detector are architectural answers to a user behavior problem — not a prompt engineering patch.
Why make confidence scoring visible?
Most AI systems hide uncertainty behind fluent prose. A system that always sounds confident but is sometimes wrong is less trustworthy than one that tells you when it's uncertain. Visible uncertainty is the mechanism through which trust is built.
Why parallel subagents instead of sequential?
Total latency equals the slowest agent, not the sum of all three. A 45-second wait creates doubt before the user has even read the output. At production scale the UX and cost advantage compounds.
Why is the orchestrator a peer, not a supervisor?
Single-purpose agents don't need coordination overhead for focused tasks. The orchestrator only activates when a task genuinely requires multiple perspectives. Keeping it as a peer destination keeps the system honest and efficient.

What I learned

01
The eval problem is underrated
I have no way to systematically verify the Red Team is finding real problems versus plausible-sounding ones. Building AI products without an eval framework is building with no quality signal.
02
Routing is where agent systems fail
Real user language is messy and context-dependent in ways keyword matching can't handle. The routing layer deserves as much attention as the agents themselves.
03
Trust is a product problem
You can't solve it with a better model. It requires intentional decisions about what the system surfaces, what it admits it doesn't know, and how it behaves when conditions change.
